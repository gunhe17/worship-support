# Logic Smart Tempo는 직접 만든 GUI 자동화로만 배치할 수 있다

Logic Pro의 Smart Tempo는 **수백 곡 배치에 쓸 수는 있지만, 공식 경로는 없다.** Logic에는 사실상 AppleScript 사전도, 헤드리스 모드도, 템포 맵을 꺼내는 전용 명령도 없다. 그래서 만들 수 있는 것은 템플릿 프로젝트를 쓰는 GUI 자동화(손쉬운 사용(Accessibility) 기반 UI 스크립팅 + 단축키)를 직접 만들고, 결과를 MIDI 파일 내보내기나 `.logicx` 내부의 ProjectData 바이너리 파싱으로 꺼내 박 시각(초)으로 바꾸는 파이프라인 하나뿐이다. BPM Counter는 80–160 BPM 범위에서 화면에 숫자만 보여 주는 실시간 플러그인이라 연구 기준선으로 쓸 수 없다. 느린 찬양은 대부분 이 범위 밑에 있어서 더욱 그렇다. "같은 엔진을 Logic 밖에서" 쓰는 경로로는 WWDC26에서 발표된 공개 프레임워크 MusicUnderstanding이 가장 깔끔하다. 다만 Logic과 같은 엔진이라는 근거는 없고, 이 Mac(macOS 26.6)에는 아직 없다. Logic 내부의 비공개 프레임워크를 직접 부르는 방법은 라이선스(SLA §2G 역공학 금지) 위반이다. 어느 경로든 macOS GUI 세션에서 돌아야 하므로 **"연산은 Kaggle에서만" 규칙의 예외를 사용자가 명시적으로 허용해야 한다.** Smart Tempo 정확도를 정량적으로 공개 평가한 자료는 하나도 없다. 그래서 이 프로젝트의 정답 세트로 처음 측정하게 되는 셈이고, 바로 그 점에서 "정답 보조"가 아니라 **"비교 대상"으로만** 넣는 것이 맞다.

## 실현 가능성 순위: GUI 자동화가 유일하게 오늘 바로 되는 길

| 순위 | 경로 | 출력 | 오늘 실행 가능? | Kaggle 규칙 | 라이선스 위험 | 확신 수준 |
|---|---|---|---|---|---|---|
| 1 | Logic GUI 자동화 + MIDI 내보내기 또는 ProjectData 파싱 | 템포 맵 → 박·마디 시각 | 가능(직접 구축, 파일럿 필요) | 로컬 Mac 예외 필요 | 낮음(통상 사용) | 중간: 문서 근거는 있으나 Logic 12.x 실측 없음 |
| 2 | MusicUnderstanding Swift CLI | 박·마디 `CMTime`, 전역 BPM, JSON | 새 OS 필요(이 Mac에는 없음) | 로컬 Mac 예외 필요 | 낮음(공개 API) | 낮음–중간: WWDC26 세션 하나뿐, 출시·정확도 미확인 |
| 3 | 상용 대안(rekordbox, Ableton, zplane AUFTAKT) | 박 그리드·워프 마커·박/다운비트 | 가능 | AUFTAKT SDK(Linux 지원 시)만 Kaggle 후보 | 낮음 | 중간 |
| 4 | Final Cut Pro 12 Beat Detection | 화면 위 박 그리드 | 파일 내보내기 경로 미확인 | 로컬 | 낮음 | 낮음 |
| 5 | Logic 비공개 프레임워크 `MAMusicAnalysis` 직접 호출 | 원시 박 목록 | 역공학 필요 | 로컬 | **SLA 위반** | 로컬 점검만 |
| 6 | BPM Counter 값 읽기 | 전역 BPM 하나(80–160) | 사실상 불가 | 로컬 | 낮음 | 높음(불가 판단) |

순위 1이 유일하게 실행 가능한 이유는 Apple 문서에 필요한 단계가 모두 있기 때문이다. Project Settings > Smart Tempo에서 Project Tempo mode를 **Adapt**로, "Set imported audio files to"를 **On**으로 두고 빈 프로젝트에 오디오를 가져오면 분석이 돌고, 감지된 템포가 프로젝트 템포 트랙에 기록된다([Apple Support 102165](https://support.apple.com/en-au/102165)). 반대로 자동화 표면은 매우 좁다. 2019년 Apple 개발자 포럼에서 확인된 Logic의 AppleScript 사전에는 `renderpreview` 하나뿐이었다. 같은 스레드에서 한 참여자는 Pro Apps 팀이 이런 자동화에 관심을 보인 적이 없다고 했다([Apple Developer Forums 115355](https://developer.apple.com/forums/thread/115355)). 공개된 Logic MCP 서버 koltyj/logic-pro-mcp도 "Logic Pro does not expose a programmatic API"라고 밝힌다. 이 도구는 AppleScript(실행·종료·파일 열기), Accessibility(상태 읽기·클릭), CGEvent(단축키), CoreMIDI, OSC를 엮어 쓰지만 템포 분석이나 가져오기 기능은 없다([koltyj/logic-pro-mcp](https://github.com/koltyj/logic-pro-mcp)). 여러 곡을 Smart Tempo로 배치 분석한 공개 도구나 사례는 찾지 못했다. Apple의 다중 파일 워크플로도 **한 곡의 스템들**을 함께 분석하는 기능일 뿐이다([Apple Artists](https://artists.apple.com/support/1465-importing-stems-into-logic-pro-with-smart-tempo)).

### 배치 파이프라인 설계와 실패 지점

템플릿 하나(Adapt, 가져온 오디오 On, 메트로놈 끔, 빈 트랙)를 만들어 두고, 곡마다 "템플릿 복제 → `open -a "Logic Pro"` → File > Import > Audio File(파일 대화상자에서 Cmd+Shift+G로 경로 입력) → 분석 완료 대기 → 저장 또는 MIDI 내보내기 → 저장 안 함으로 닫기"를 Accessibility 스크립트(System Events, Hammerspoon, atomacos 계열 Python 래퍼 [pyuiauto](https://pypi.org/project/pyuiauto/) 등)로 반복한다. 입력 파일은 먼저 태그 없는 일반 WAV/AIFF로 정규화해야 한다. 상업 음원에는 템포 태그가 들어 있는 경우가 많고, 그러면 Edit > Tempo > Remove Tempo Information으로 지우기 전까지 재분석이 되지 않는다([Sound On Sound](https://www.soundonsound.com/techniques/logic-pro-using-smart-tempo)). 깨질 지점도 예상된다. Free Tempo Recording의 "Ask" 대화상자, MIDI 템포 가져오기 확인창([Apple Community](https://discussions-jp-prz.apple.com/thread/251126695)) 같은 모달, Auto 모드에서 메트로놈이나 다른 리전이 있어 템포가 고정되는 경우, Logic 업데이트로 메뉴·AX 구조가 바뀌는 경우다. 곡당 소요 시간은 어떤 출처에도 없다. 열기·가져오기·분석·닫기를 합쳐 1–2분으로 잡으면 수백 곡에 5–15시간, 즉 하룻밤 분량이라는 것은 **측정값이 아닌 추정**이므로 10곡 파일럿으로 먼저 재야 한다. Scripter(MIDI FX JavaScript)는 `GetTimingInfo()`로 현재 템포만 실시간 재생 중에 읽을 수 있고 출력도 `Trace()` 콘솔뿐이다([Logic 10.4.5 guide](https://help.apple.com/logicpro/mac/10.4.5/en.lproj/lgcee186be46.html)). 곡 길이만큼 재생해야 하므로 배치에는 맞지 않는다. 헤드리스 실행은 불가능하다. 로그인된 GUI 세션과 Accessibility 권한이 필요하므로 서버나 CI에서는 돌릴 수 없고, 잠자기와 화면 잠금을 끈 전용 Mac에서 밤새 돌리는 것이 현실적이다.

**Kaggle 규칙과의 충돌:** 이 경로는 사용자의 로컬 Mac에서 오디오 분석(Logic 내부의 신경망 추론)을 수백 번 돌리는 일이므로 "로컬은 편집·문법 검사·CLI만" 규칙에 정면으로 걸린다. Kaggle에는 macOS가 없으니 우회할 방법도 없다. 진행하려면 사용자가 "Logic 배치 한정 로컬 연산 허용" 같은 명시적 예외를 내려야 한다. 그 전까지 에이전트가 할 수 있는 일은 스크립트 작성과 문법 검사까지다.

## 결과 꺼내기: 템포 트랙을 거쳐야 박 시각이 된다

Smart Tempo의 **박 마커**는 오디오 파일에 붙는 분석 데이터이고, 프로젝트 **템포 맵**은 전역 Tempo 트랙에 있는 별개의 이벤트 목록이다. Smart Tempo 편집은 원본 오디오가 아니라 "Logic이 파일을 프로젝트 템포에 맞추는 데 쓰는 템포 정보"만 바꾼다([Apple guide](https://help.apple.com/logicpro/mac/10.4/en.lproj/lgcp2a428fed.html)). 이 파일 내부 정보는 문서화되지 않은 독자 청크에 저장되며, 공개 명세나 파서는 없다. 그러니 박 정보를 꺼내려면 Adapt 모드나 "Apply Region Tempo to Project Tempo"로 먼저 Tempo 트랙에 옮겨야 한다([Logic 10.4 guide](https://help.apple.com/logicpro/mac/10.4/en.lproj/lgcp9281e70c.html)). 이때 핵심 설정이 두 가지다. Flex & Follow를 "On + Align Bars and Beats"로 두면 변화가 감지된 박마다 템포 이벤트가 찍힌다. Export Tempo Resolution을 **Beats**로 두면 박 단위 템포가 평활화 없이 기록된다(Smoothed는 박 사이 변동을 뭉갠다)([Logic 10.4 guide: Smart Tempo settings](https://help.apple.com/logicpro/mac/10.4/en.lproj/lgcp6ad7156e.html)). 이렇게 하면 템포 맵이 사실상 박 목록과 같아진다.

꺼내는 방법은 두 가지다. **경로 A(MIDI)**는 공식 기능이다. File > Export > Selection as MIDI File은 Format 1 SMF를 쓴다([Logic 10.1 guide](https://help.apple.com/logicpro/mac/10.1/en.lproj/lgcpdf6a3851.html)). 하지만 Apple 문서는 내보낸 파일에 템포·박자표 메타 이벤트가 들어간다고 명시하지 않는다. 사용자 보고도 엇갈린다. Logic 8에서는 템포가 빠졌다는 보고가 있고([Logic Users Group](https://logic-users-group.com/threads/exporting-tempo-map-time-signatures.991/)), Logic 10.3에서는 템포는 들어갔지만 bar 1의 SMPTE 위치 때문에 타임코드가 어긋났다는 보고가 있다([Logic Users Group](https://logic-users-group.com/threads/smpte-sync-issue-when-exporting-midi-from-logic-to-pro-tools.10531/)). 곡 전체를 덮는 빈 MIDI 리전을 하나 만들어 선택한 뒤 내보내는 요령은 문서화되지 않았다. 그러므로 현재 Logic 12.x에서 `set_tempo`·`time_signature`가 실제로 담기는지 mido로 한 번 확인해야 한다. **경로 B(ProjectData)**는 GUI 내보내기 단계가 없어 배치에 더 잘 맞는다. MIT 라이선스의 LogicProFormatWriter가 `Alternatives/000/ProjectData`를 역공학해 정리해 두었다. 템포 맵은 `qSvE` 레코드에 있고, 해상도는 960 PPQ, 이벤트는 32바이트, 위치는 `+0x04` uint64(= 38400 + tick), 템포는 `+0x10` uint32(= round(BPM×10000)), `+0x18`에는 0.5 ms 단위 절대시간 캐시가 있다([PROJECTDATA_FORMAT.md](https://github.com/jonkubis/LogicProFormatWriter/blob/main/PROJECTDATA_FORMAT.md)). 다만 이 프로젝트는 *쓰기* 라이브러리이고, 기준 버전이 11.2.2와 12.0.1로 문서 안에서도 엇갈린다. Smart Tempo가 만든 맵을 그대로 읽을 수 있는지도 확인되지 않았다. Logic 버전마다 120→130 BPM처럼 알려진 맵으로 재현 검증을 해야 한다. 템플릿을 저장하는 것은 Logic의 통상 사용이고, 저장된 파일을 읽는 것은 Logic 소프트웨어 자체의 역공학이 아니다. 그래도 SLA 해석에 대해서는 포럼에 이견이 있다([Logic Users Group](https://logic-users-group.com/threads/logic-and-lso-file-format-specs-available.2874/)).

박 시각(초)으로 바꾸는 계산은 단순하다. 구간별로 일정한 템포를 적분해 t(tick) = t0 + Σ Δtick/PPQ × 60/BPM를 구하고, PPQ의 정수배 위치가 박, 박자표에 따른 마디 경계가 다운비트다. SMF라면 `pretty_midi.PrettyMIDI(path).get_beats()`와 `get_downbeats()`가 이 계산을 해 준다([pretty_midi docs](https://craffel.github.io/pretty-midi/); [mido docs](https://mido.readthedocs.io/en/latest/files/midi.html)). 함정은 네 가지다. 첫째, SMF의 시각 0과 오디오 파일 시작점의 오프셋이다. "Trim start of new regions"는 리전 시작을 첫 다운비트로 옮기므로 리전 위치를 반드시 기록해야 한다. 둘째, pretty_midi의 박 단위는 박자표 분모를 따른다(6/8이면 8분음표). 셋째, x2·/2 옥타브 오류다. Apple 스스로 Adapt 모드가 "원하는 템포의 두 배나 절반"을 잡을 수 있다고 인정한다([Apple HT208458](https://support.apple.com/kb/HT208458)). 넷째, 템포 곡선은 SMF에서 계단으로 근사된다. 해상도 자체는 문제가 아니다. 960 PPQ와 µs 단위 템포는 ±70 ms 채점 창보다 훨씬 촘촘하고, 실제 오차는 Smart Tempo가 템포 트랙으로 양자화·평활화하는 과정에서 생긴다. 싸게 검증하려면 Logic에서 클릭 트랙을 렌더링하거나 ProjectData의 절대시간 캐시를 계산된 박 시각과 대조하면 된다.

## 같은 엔진을 Logic 밖에서 쓰는 길은 사실상 막혀 있다

**공개 API (확신: 낮음–중간):** WWDC26 세션 253은 `MusicUnderstanding` 프레임워크를 소개했다. `MusicUnderstandingSession(asset:)` → `analyze()`를 호출하면 `RhythmResult`가 `beats: [CMTime]`, `bars: [CMTime]`, 전역 `beatsPerMinute`을 돌려주고, 기기 안에서 오프라인으로 돌며 결과는 `Codable`이라 JSON으로 바로 덤프할 수 있다([WWDC26 session 253](https://developer.apple.com/videos/play/wwdc2026/253)). Final Cut Pro 12(2026년 1월)의 Beat Detection이 이 프레임워크를 쓴다고 한다. 3분 클립을 5초 안에 분석했다는 리뷰도 있다([Larry Jordan](https://larryjordan.com/articles/the-new-beat-detection-in-final-cut-pro-12-is-simple-and-effective/)). 세션은 Logic을 언급하지 않는다. 템포 곡선, 박자표, 신뢰도 출력도 없고, 정확도 수치도 제시하지 않는다. 최소 OS 버전은 확인하지 못했다(macOS 27로 추정). 이 Mac(macOS 26.6)에서는 `/System/Library/Frameworks/MusicUnderstanding.framework`가 보이지 않았다[로컬 점검]. 정리하면 이 경로는 **세션 영상 하나에 기댄 최신 주장**이다. 출시 여부, 정확도, Logic 엔진과의 동일성이 모두 검증되지 않았다. 새 OS가 깔린 Mac이 생기면, 파일을 순회하며 `RhythmResult` JSON을 쓰는 50줄짜리 Swift CLI가 Logic GUI 자동화보다 훨씬 견고한 배치가 된다. 그래도 로컬 Mac 연산이라는 점은 같으므로 Kaggle 규칙 예외가 필요하다. MusicKit과 Apple Music API에는 곡 BPM 속성이 없다([Dev Forums 726626](https://developer.apple.com/forums/thread/726626)). AVFoundation, SoundAnalysis, ShazamKit에도 템포·박 출력은 없다.

**비공개 프레임워크 (확신: 로컬 점검만, 재현 가능하지만 외부 검증 없음):** 설치된 Logic 12.2 바이너리를 `nm`/`strings`/`otool`로 읽기 전용 점검한 결과는 다음과 같다(실행하거나 로드하지는 않았다). 엔진은 `Contents/Frameworks/MAMusicAnalysis.framework`(내부 코드명 "Metro")에 있고, C++ 심볼로 `CreateAnalyzer`, `IsHalfTempo`/`IsDoubleTempo`, `QPMTempoListFromBeats` 등을 내보낸다. 문자열로는 `DownBeatTrackerTCNHMM`, `.beat_activations`, `downbeathmm.mlbf`, `jointtimesighmm.mlbf`가 보이고, Core ML 모델 `DownbeatTrackerCondMPS.mlmodelc`도 들어 있다. 즉 **TCN 박/다운비트 활성화 + HMM 디코딩**이라는, madmom·Beat This!와 같은 계열의 구조로 보인다. 내부 평가 클래스(`CCompareBeatsFMeasure`, `CCompareBeatsCemgil`)도 있다. Smart Tempo가 iOS Music Memos와 같은 감지 기술이라는 점은 Apple이 확인했다([CDM](https://cdm.link/2018/01/logic-pro-x-10-4-new-effects-and-play-and-mix-audio-without-a-click/)). 하지만 이 프레임워크를 부르려면 문서화되지 않은 C++ 클래스 레이아웃을 복원해야 하고, 이는 SLA §2G가 금지하는 역공학이다. Logic이 업데이트될 때마다 깨지기도 한다. **권장하지 않는다.** BPM Counter도 시스템 Audio Unit이 아니다. 이 Mac의 `auval -a` 목록에 없으므로[로컬 점검] AU Lab, pedalboard, JUCE 호스트에서 불러올 수 없다. 공식 문서상으로도 조정 파라미터나 출력·전달 기능이 없는 표시 전용 플러그인이다([Logic Effects guide](https://help.apple.com/logicpro-effects/mac/10.1/en.lproj/lgcef24f3fd9.html)).

**라이선스:** 확인할 수 있었던 Logic Pro SLA는 2013년판(EA1004)뿐이다. 이 판은 역공학, 디컴파일, 파생물 제작을 금지하고(§2G), 번들된 구성요소 전체를 "Apple Software"로 정의하며(§1A), 네트워크 공유 실행을 금지한다(§2E)([Logic Pro SLA](https://www.apple.com/legal/sla/docs/LogicPro.pdf)). 자동화, 벤치마크, ML 사용을 금지하는 조항은 없었다. 따라서 위험은 다음과 같이 갈린다. 자신이 라이선스를 가진 Mac에서 GUI를 자동 조작하고 템포 맵을 내보내 연구 수치를 보고하는 일은 통상 사용이고, MusicUnderstanding 같은 공개 API는 개발자 약관 안의 사용이다. 둘 다 위험이 낮다. 비공개 프레임워크 로드는 위험이 높다. 현행 Logic 12 / Apple Creator Studio 구독 약관은 확보하지 못했으므로 결론을 확정하기 전에 확인해야 한다.

## 정확도는 아무도 재지 않았다: 직접 측정해야 한다

Logic Smart Tempo, BPM Counter, FCP Beat Detection, MusicUnderstanding 중 어느 것도 MIR 벤치마크나 오픈소스 트래커와 정량 비교한 공개 평가가 없다. 리뷰는 모두 정성적이다. Sound On Sound는 대부분의 팝에서 "works really well"이라고 하면서도 6/8을 3/4로 읽은 사례를 적었다([Sound On Sound](https://www.soundonsound.com/techniques/logic-pro-using-smart-tempo)). 140 BPM 하프타임 트랩을 70 BPM으로 잡거나 첫 다운비트를 틀리는 사례도 소개했다([SOS workshop](https://www.soundonsound.com/node/4918970)). 상용 DJ·DAW 도구에도 독립 벤치마크가 없다. Engine DJ는 내부 데이터가 있다고만 말한다([Engine DJ community](https://community.enginedj.com/t/best-analytical-software-for-bpm-key-downbeat-cues/40389)). Schreiber 등의 템포 추정 리뷰도 연구 시스템만 다룬다([TISMIR 2020](https://transactions.ismir.net/articles/189)). 이 공백이 연구 설계를 정한다. 첫째, Logic 출력은 **정답 보조로 쓸 근거가 없다.** 검증되지 않은 트래커 출력을 정답에 섞으면, 같은 계열(TCN+HMM) 구조를 가진 Beat This!·madmom 점수가 부풀려지는 순환이 생긴다. 둘째, **비교 대상으로는 가치가 있다.** 이 프로젝트의 박 시각 정답 세트로 Smart Tempo의 F-measure·CMLt·AMLt를 처음 공개적으로 잴 수 있다. 측정할 것은 사람이 x2·/2와 다운비트를 고치기 전의 **원시 출력**이어야 한다. 옥타브 오류가 흔하리라 예상되므로 CMLt와 AMLt의 차이가 핵심 지표가 된다. 느리고 루바토가 많은 찬양 인트로는 최신 트래커들이 박 배치와 박자 일관성에서 따로따로 실패하는 영역이다([arXiv 2605.12287](https://arxiv.org/pdf/2605.12287)). 이 구간에서 Apple 엔진이 다르게 행동하는지가 가장 흥미로운 비교점이다.

## 상용 대안: rekordbox가 가장 기계 친화적이고, AUFTAKT만 Kaggle 가능성이 있다

Logic 대신, 또는 Logic과 함께 "상용 기준선"을 넣는다면 **rekordbox**가 가장 실용적이다. 폴더를 통째로 컬렉션에 넣고 일괄 분석(가변 템포용 Dynamic 모드)한 뒤, XML의 `TEMPO` 요소(`Inizio` 초, `Bpm`, `Metro`, `Battito`)를 읽거나([pyrekordbox XML](https://pyrekordbox.readthedocs.io/en/stable/formats/xml.html)) ANLZ 파일의 `PQTZ` 태그에서 박 하나하나의 시각을 pyrekordbox로 읽으면 된다([pyrekordbox ANLZ](https://pyrekordbox.readthedocs.io/en/stable/tutorial/anlz.html)). XML에 BPM 변화점을 넣으려면 Preferences > Advanced 옵션을 켜야 한다([Mixed In Key](https://mixedinkey.com/workflows/export-cue-points-to-rekordbox/)). 일부 MP3는 디코더에 따라 약 26 ms 선행 오프셋이 생기므로 WAV로 넣는 편이 안전하다([Engine DJ community](https://community.enginedj.com/t/beatgrid-import-incorrect-for-traktor-or-rekordbox/42780)). **Ableton Live 11+**는 Live Object Model의 `Clip.warp_markers`가 (샘플 시각, 박 시각) 쌍을 돌려주므로 Max for Live로 덤프할 수 있다([Cycling '74 LOM](https://docs.cycling74.com/apiref/lom/clip/)). 하지만 자동 워프 마커가 성기면 박 사이가 보간된다. **zplane AUFTAKT v4**는 DNN 기반으로 박, 다운비트, 급격한 템포·박자표 변화를 내고, SDK 문서에 명령줄 사용 예가 있으며 Mac/PC 데모 앱도 있다([zplane](https://licensing.zplane.de/technology); [SDK PDF](https://licensing.zplane.de/uploads/SDK/AUFTAKT/V4/manual/AUFTAKT_v4_sdk_documentation.pdf)). 과거 Ableton Live 5–9와 djay가 이 엔진을 썼다. 라이선스 가격과 Linux 지원은 확인하지 못했다. 그래도 **Kaggle 규칙을 지킬 가능성이 있는 유일한 상용 후보**다. Serato(GEOB 태그, [serato-tools](https://www.piwheels.org/project/serato-tools/))와 Traktor(collection.nml, 사실상 고정 템포 그리드)는 형식이 역공학 기반이라 2순위다. Superpowered, Mixed In Key, Cyanite는 전역 BPM만 준다. Spotify Audio Analysis는 2024-11-27부터 신규 앱에 막혔다([Spotify blog](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api)). Cubase, Studio One, Melodyne은 곡마다 GUI 조작이 필요해 배치에 맞지 않는다. AUFTAKT SDK를 빼면 모두 로컬 GUI 실행이므로 Logic과 똑같이 Kaggle 규칙 예외가 필요하다.

## Conclusion

이 조사로 질문의 성격이 바뀐다. "Logic을 배치로 돌릴 수 있는가"는 기술 문제라기보다 **비용과 규칙의 문제**다. 기술적으로는 템플릿, Accessibility 스크립트, ProjectData 파서로 하룻밤 배치가 가능해 보인다. 그 대가는 로컬 연산 예외, 버전마다 깨지는 UI·바이너리 의존성, 그리고 어디에도 없는 MIDI 템포 내보내기 검증이다. 그래서 순서가 중요하다. 예외를 승인받았다면 먼저 Logic 12.x에서 알려진 템포 맵(예: 120→130 BPM)과 클릭 트랙으로 "MIDI에 템포가 담기는가 / ProjectData 파서가 맵을 재현하는가"를 한 번 확인한다. 이어서 10곡 파일럿으로 곡당 시간과 실패율을 잰다. 그 결과를 보고 수백 곡으로 넓힌다. 로컬 점검에서 드러난 TCN+HMM 구조가 맞다면 Logic은 Beat This!·madmom과 독립적인 기준선이라기보다 **같은 계열의 상용 구현**이다. 따라서 비교 결과의 가치는 "누가 더 정확한가"보다 "Apple의 학습 데이터와 HMM 사전 설정이 느린 찬양의 옥타브·다운비트 오류를 다르게 내는가"에 있다.

가장 나은 장기 경로는 Logic이 아닐 수 있다. MusicUnderstanding이 실제로 출시되었다면 GUI 없이 박·마디 시각을 JSON으로 주는 유일한 Apple 경로이고, 배치 견고성에서 Logic 자동화를 크게 앞선다. 다만 이것이 Logic Smart Tempo와 같은 엔진이라는 증거는 없으므로, 둘은 "Apple 엔진 하나"가 아니라 별도의 두 비교 대상으로 다뤄야 한다. Kaggle 규칙을 깨지 않는 상용 기준선이 꼭 필요하다면, 검토할 가치가 있는 것은 zplane AUFTAKT SDK의 Linux 라이선스 문의 하나뿐이다.
