# 진행 기록

## 2026-09-29

### 1. 계획 (완료)
- 사용자 방향: 가사보다 **전체 악보를 MusicXML로 옮기는 접근**이 중요
- 정답이 있어야 음표 정확도를 잴 수 있으므로, 퍼블릭 도메인 리드시트(OpenEWLD)를 렌더링해 정답 세트를 만듦. 실제 찬양 악보는 정답 없이 되는 검사만
- 채점 도구: musicdiff (`_diff_omr_ned_metrics(pred, gt, detail)` → OMR-NED + 항목별 편집 수)
- Flat API·Gemini는 키가 필요해 보류, 무료 후보(Audiveris, Qwen3-VL)부터 진행

### 2. 정답 세트·채점 도구 준비 (완료)
- 정답 세트 원천: **OpenEWLD** (퍼블릭 도메인 리드시트 502곡, MIT, 멜로디·코드·가사 포함 MusicXML)
- 로컬에서 1곡으로 사전 확인만 함(수 초): music21 파싱 → Verovio SVG 렌더링 시 가사 94개·코드 25개 모두 그려짐, musicdiff 자기 자신과 비교 시 OMR-NED 0.0 확인. PNG 변환(cairo)은 로컬에 시스템 라이브러리가 없어 Kaggle에서 처리
- musicdiff API: `_diff_omr_ned_metrics(pred, gt, DetailLevel.X)` → `omr_ned`, `gt_numsyms`, `pred_numsyms`, `omr_edit_distance`

### 3. 후보 1 — Audiveris (Kaggle CPU 커널 `gunhe17/sheet-xml-audiveris`, 진행 중)
- `kaggle/audiveris/run.py`: 세트 A 20곡 선정(시드 0, 조건: 1성부·코드≥4·가사 음표≥10·3/4 또는 4/4·16~48마디·1페이지) → 렌더링(clean 1650px PNG / lowres 900px JPEG q60) → Audiveris(A는 eng, B는 kor+eng, 1600px 미만은 2배 확대) → musicdiff 채점(notes·signatures·barlines·chords·lyrics·all) → 세트 B 박자 정합성
- 이전 시행착오 반영: `.deb` 실행파일 경로 직접 탐색, legacy 포함 tessdata

### 4. 후보 2 — Qwen3-VL → ABC → MusicXML (준비 완료, 커널 1 결과 대기)
- `kaggle/vlm/run.py`: 커널 1 출력(이미지·정답)을 `kernel_sources`로 재사용. Qwen3-VL-4B(fp16, max_pixels 2048×28×28)에 ABC 2.1로 전사 요청 → music21로 MusicXML 변환 → 같은 기준으로 채점
- **가사는 빼고** 음표·코드·반복 구조만 요청 (사용자 우선순위 + 생성 토큰 절약)
- **사용자 지시: 연산은 무조건 Kaggle에서.** 2번 항목의 로컬 사전 확인(Verovio 렌더링·musicdiff 1곡, 수 초)도 이후로는 하지 않음. 로컬은 파일 편집·문법 검사·Kaggle/git CLI만
- **Audiveris 커널 v1**: 세트 A 20곡 생성·렌더링은 정상. 그러나 **Audiveris가 MusicXML을 하나도 만들지 못함** → 채점 전부 1.0(출력 없음)
  - 원인: `UnsatisfiedLinkError: Unable to load library 'gtk-3'` — Audiveris가 `-batch`에서도 시작 시 JNA로 libgtk-3을 로드함. 이전 OMR 커널은 openjdk 설치 때 딸려 들어와서 문제가 안 드러났던 것
  - 부수 문제: OpenEWLD 저장소 전체와 중간 이미지를 `/kaggle/working`에 둬서 커널 출력이 수천 개 파일로 커짐 → 다운로드 지연. `kaggle kernels output --file-pattern '^(out/|.*\.log$)'`로 필요한 것만 받음
- **v2**: `libgtk-3-0 libfreetype6 fontconfig` 추가, 저장소 복제·중간 파일·tessdata를 `/tmp`로 이동
- **v2 성공** (Audiveris 장당 중앙값 21초, 최대 49초 / Kaggle CPU): 세트 A 40장·세트 B 16개 MusicXML 모두 생성

### 6. 집계 커널 (`gunhe17/sheet-xml-summary`, Kaggle CPU) + Audiveris 파트 문제 발견
- 박자 정합성(마디 정규식 수정 후): Audiveris 세트 A 94% · 세트 B(실제 찬양 악보 16개) 62% / Qwen은 변환된 일부만(A 5곡분, B 5개) 있어 비교 의미 없음
- **Audiveris가 마디를 정답의 약 2배로 냄**(2,495 vs 1,246) → 확인해 보니 **한 성부 리드시트를 파트 2개로 나눔**: P1(주 멜로디, 예: 음표 82개)과 P2(잘못 분리된 파트, 음표 33·쉼표 13). 정답은 1파트라 P2 전체가 오류로 채점돼 **Audiveris 점수가 불리하게 계산됐을 가능성**
- **v3 커널 `gunhe17/sheet-xml-audiveris-v3` 푸시** (`kaggle/audiveris-v3/run.py`, CPU)

## 19. 가설 시험: 오선 진하기로 악보별 잉크 기준 정하기 (2026-09-30)

- 커널 gunhe17/sheet-ink-diag (kaggle/ink-diag, CPU), 6장: 기준 T = 오선 줄 회색 90백분위 + 0.35×(종이 − 그 값). 기존 = min(Otsu, 150).
- 결과(오선 회색 p50/p90 → T): 예수전도단 156/183 → 208, 힐송 157/171 → 200, 아가파오 152/160 → 193, 피아워십 144/160 → 193, 제이어스 65/106 → 158, 마커스 3/32 → 110.
  - 예수전도단·힐송·아가파오: 기존 기준(150)보다 오선 줄 자체가 연함 → 기존 방식에서 오선이 사라진 이유가 수치로 확인됨. 새 기준에서 오선·꼬리·마디선 복구(그림의 빨강), 워터마크(예수전도단 화요모임 로고, 아가파오 AGA 로고)는 제외(하늘색).
  - 피아워십 분홍·제이어스 회색 워터마크도 제외.
  - 오선에 이어진 덩어리 높이(워터마크 다리 효과 점검): 중앙값 기준 변화 ≤0.4칸(예수전도단 7.39→7.80) → 워터마크를 타고 가사가 붙는 현상은 보이지 않음. 늘어난 부분은 복구된 연한 꼬리로 추정(눈 확인은 페이지 단위만).
  - 마커스(깨끗한 악보)는 T가 110으로 기존보다 낮아짐 → 기준을 max(기존, 새 값)으로 두면 깨끗한 악보는 그대로.
- 판단: 6장에서는 유효. 한계 — 워터마크가 오선만큼 진한 악보는 이 방법으로 못 가름(6장 중에는 없음).

## 20. 알고리즘 시험: 문서별 잉크 기준(0단계) + 오선 몸통 통째 + 튀어나온 음표 (2026-09-30)
- 사용자 의도: 수치가 아니라 문서마다 오선 진하기를 먼저 분석해 그 문서의 기준으로 이후를 진행하는 알고리즘.
- 구현(kaggle/regions-calib, 6장): calibrate_ink() — 오선 줄 픽셀(위아래 1px 중 최소) 회색 p50/p90, 종이(p90) → T = max(min(Otsu,150), p90 + 0.35×(종이−p90)); 오선이 무채색이면 연한 유채색 픽셀 제외; 오선 못 찾음·저대비는 표시. 이후 오선 연결 추적·행 분할·검출 모두 이 잉크 사용. 오선 영역 = 몸통 직사각형(맨 윗줄~맨 아랫줄, 오선 폭) + 이어진 음표.
- 결과(기존 regions-100 대비):
  - ③ 소실: 예수전도단 8→0, 아가파오 6→0, 피아워십 6→0, 힐송 3→0. 오선 PNG를 열어 보면 오선 줄·꼬리·마디선·음표 머리 모두 있음(예수전도단 s03, 아가파오 s03, 힐송 s01 확인).
  - 워터마크: 예수전도단 오선 PNG에 가사 끌려옴 없음(워터마크는 행 PNG 배경에 옅게 남음).
  - 마커스(깨끗함): 기준 148로 기존과 같음, 행 수·오선 박스 완전히 동일.
  - 아가파오 행 21→13: 이전에 연한 오선에서 새어 나오던 얇은 조각 행(0.07–1.1칸)이 사라짐 → 줄 사이마다 코드 행·가사 행 2개로 정리됨.
  - 예수전도단 ① 2→4: 늘어난 2건은 오탐 — 연했던 가사 글자가 잉크로 복구되면서 '룩'·'주' 아랫부분을 붙임줄 모양으로 잘못 봄(검출 규칙 쪽 문제, 알고리즘 문제 아님).
- 판단: 6장에서 가설 유효. 남은 과제는 검출 규칙의 한글 조각 오탐.

## 21. 100장 적용: 문서별 잉크 기준 + 오선 몸통 통째 (2026-09-30)
- kaggle/regions-100 = regions-calib 알고리즘(6장 제한 해제). 이전 결과는 results/regions-100/regions_before_calib.json.
- 1차(v11): "연한 유채색 = 워터마크" 색 규칙이 23장에서 진한 빨강 코드·파랑 도돌이/Fine까지 지움(부흥한국 「부흥」 44k px, 어노인팅 23k px) → 코드 행이 행 분할에서 빠짐. 피아워십 분홍 워터마크는 진하기로 이미 빠져 색 규칙이 지운 픽셀 0 → 색 규칙 삭제(v12).
- 2차(v12): 높아진 기준이 획 가장자리·옅은 점까지 잉크로 잡아 행 사이 좁은 빈 띠가 메워짐 → 붙임줄 행이 가사 행과 합쳐짐(기프티드 b07_r01). 행 분할의 빈 띠 찾기만 기존 기준(min(Otsu,150))으로 되돌림(v13). 문서별 기준은 오선 영역 오려내기에만 사용.
- 최종(v13) vs 이전: ③ 67 → 0. 오선 수 698 동일, 행 2,031 → 1,983(얇은 조각 행 386 → 358, 3.5칸 넘는 행 87 → 78: 병합 없음). ② 2건 그대로(마커스 「주의 이름 높이며」, 위러브 1). ① 21 → 19: 히즈윌 3건은 연한 음표 머리·붙임줄이 이제 오선 영역으로 들어가 가사 행이 깨끗해짐(그림 확인, 진짜 해소). 예수전도단 새 2건은 가사가 진하게 복구되며 생긴 한글 조각 오탐. 기준이 올라간 문서 60장(30 이상 20장), 저대비·오선 못 찾음 표시 0장.

## 22. 오선 누락 원인 분석 (2026-09-30)
- 진단 커널 gunhe17/sheet-staff-diag (kaggle/staff-diag): staff_systems() 단계 재현 — 후보 가로선(행별 페이지 폭 대비 덮는 비율 >18%), 묶음(간격 ≤ 2.5×중앙 간격), 5줄 이상만 채택.
- 공통 원인: 놓친 오선 모두 **5줄 중 1줄이 후보에서 빠져 4줄 묶음 → 5줄 조건에 탈락**.
  - 위러브1 21–28마디: 찾은 줄 1131·1146·1160·1187, 네 번째 줄(≈1173)은 픽셀 두 행에 갈라져 1173행 11%, 1174행 18%만 덮음(합 ≈29%) → 한 행씩 재는 18% 기준 미달. 원본(966px) 확대 그림에서 오선 줄 굵기·진하기가 줄마다 다름(1px 안티에일리어싱 선이 픽셀 경계에 걸쳐 연한 두 줄로 그려짐).
  - 마커스 「주의 이름 높이며」 5번째 오선: 찾은 줄 1377·1392·1405·1431, 네 번째 줄(≈1418) 자리는 덮는 비율 5% 미만. 원본 확대 그림에서 그 줄이 다른 줄보다 훨씬 연함.
  - 즉 "기울어짐"이 아니라 가는(1px) 선이 픽셀 경계에 걸려 연해지고 두 행으로 갈라지는 문제. 앞의 "기울기" 설명은 틀렸고, 행 합치기(위아래 2px)가 효과 있었던 이유는 이 갈라짐 때문.
- 부수 발견: 6줄 묶음 3개(위러브1 g6·g11, 마커스 g12) — 라벨 상자 테두리·반복 괄호선이 오선 위 한 칸(또는 6px) 자리에 붙어 묶음에 섞임 → 오선 박스가 한 칸 더 커짐.
- 고칠 방향(미적용): ① 선 후보를 위아래 1–2px 합쳐 재기, ② 4줄 묶음 중 간격 하나가 ≈2배면 빠진 줄을 끼워 넣어 인정, ③ 6줄 이상이면 간격이 가장 고른 연속 5줄만 택하기, ④ 선 찾기에도 0단계 문서별 잉크 기준 적용.
