# Worship 10/14 팀 회의록

- 회의 기준일: 2026-10-14

## 1. 개발 방향

새로운 개념을 바로 구현하기보다 검증된 레퍼런스를 먼저 조사하고 전체 구조를 이해한 뒤 탑다운 방식으로 설계한다. 각 담당자는 테이블·화면만 만드는 것이 아니라 **왜 그 구조를 선택했는지 설명할 수 있는 수준**까지 설계한다.

## 2. 계정과 로그인

- V1은 이메일+비밀번호 자체 로그인을 제거하고 Google·Kakao 소셜 로그인만 사용한다.
- User는 이메일 문자열이 아니라 Provider의 고유 식별자를 기준으로 식별한다.
- User와 Workspace 소속 상태(Member)는 분리한다.

## 3. Workspace와 관리자

- Workspace마다 관리자는 정확히 1명이다.
- 관리자는 Workspace의 모든 Document를 목록 수준에서 볼 수 있다.
- RESTRICTED Document의 실제 내용은 해당 Document 권한이 있어야 볼 수 있고, 관리자라는 이유만으로 편집 권한은 생기지 않는다.
- 관리자 이전은 상대 수락을 기다리지 않고 재인증·최종 확인 후 즉시 처리한다. 기존 관리자는 일반 Member가 된다.
- `Workspace`의 사용자 노출 명칭은 추후 결정한다.
- 서비스 내 별도 관리자 문의 기능은 두지 않고 필요한 경우 운영 연락처만 제공한다.

## 4. Member 나가기와 강제 퇴장

- 자발적으로 나간 Member는 Soft Delete 상태로 보존한다.
- 같은 User가 다시 참여하면 기존 Member를 복구하고 남아 있는 Document 권한도 복원한다.
- 강제 퇴장된 Member는 기존 레코드를 보존하되, 재가입 시 같은 User 아래 새 Member를 생성한다.
- 강제 퇴장 전의 Document 권한은 자동 복원하지 않는다.

## 5. Document 권한과 OWNER

- Document 역할은 `OWNER / EDITOR / VIEWER` 세 개만 사용한다. 기존 `책임자` 역할은 제거한다.
- 모든 Document는 항상 정확히 1명의 OWNER를 가진다.
- 일반 소유권 이전은 상대 수락 후 완료되며, 이전 전까지 기존 OWNER를 유지한다.
- OWNER가 Workspace를 자발적으로 나가거나 강제 퇴장되면 Workspace 관리자가 수락 없이 즉시 OWNER를 넘겨받는다.
- 일반 소유권 이전 뒤 기존 OWNER에게 EDITOR·VIEWER 권한을 자동 보존하지 않는다.
- 일반 Document URL과 외부 공유용 ViewLink를 분리한다.
- 권한 없는 Workspace Member의 접근 요청은 OWNER만 승인하며 VIEWER 또는 EDITOR를 부여한다.

## 6. Team 정책

- Team은 더 이상 Document 권한의 주체가 아니다.
- Team은 권한 설정 화면에서 여러 Member를 빠르게 선택하기 위한 편의 그룹으로만 사용한다.
- Team A를 선택하면 그 시점의 A 소속 Member들에게 개인 권한이 생성된다.
- 이후 Team 구성원이 바뀌어도 기존 Document 권한은 자동 변경되지 않는다.
- 기존 `개인 제외` 기능은 제거한다.

## 7. 삭제 정책

- 사용자에게 제공하는 삭제는 기본적으로 Soft Delete로 처리한다.
- 초기에는 자동 Purge를 구현하지 않는다.
- 운영자가 예외적으로 Hard Delete할 때는 참조 관계, 복구 필요성, 감사·보안·법적 보존 필요성을 확인한다.
- Hard Delete 시 대상·사유·실행자·실행 시각을 기록한다.
- Archive 상태는 현재 별도로 도입하지 않는다.

## 8. 재설계가 필요한 영역

- `ServiceOccurrence / 예배 회차`: 유지·대체·제거를 아직 확정하지 않는다.
- `Document / Template / 실제 생성 결과물`: 편집 구조와 결과물 경계를 다시 설계한다.
- Workspace 최종 명칭, 곡·참고 영상 등록 정책과 부적절한 콘텐츠 처리도 추가 논의한다.

## 9. AI 분석과 예배 자료 구현 경계

- YouTube 링크 입력 → AI 분석 → BPM·Key 등 곡 요소 후보를 선택하는 구간까지 건희가 담당한다.
- 성민은 AI 분석 결과를 받은 이후의 곡·콘티·블록·템플릿 및 사용자 UI 흐름을 담당한다.
- 외부 AI/분석 인프라가 완성되기 전에는 해당 구간을 Mock/Stub으로 대체해 전체 흐름을 먼저 완성한다.

## 10. 프론트 디자인 공통 기준

성진과 성민이 실제 서비스 또는 디자인 시스템 중 하나를 공통 레퍼런스로 선정한다. 이후 빠르게 UI를 구현하더라도 화면마다 서로 다른 스타일을 임의 적용하지 않고, 선정한 레퍼런스의 레이아웃·컴포넌트·상호작용 원칙을 공통 기준으로 사용한다.
